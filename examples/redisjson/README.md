# Redis JSON examples

These examples exercise two Redis interaction styles generated by
`NSmithy.Bote`:

- `chat` models a durable command stream and a separate event stream. Posting a
  message is one-way; clients follow `MessagePosted` events independently.
- `inventory` models unary request/reply. Requests are durable Redis Stream
  entries, while replies use temporary correlated Pub/Sub channels.

## Projects

- `chat`: the model and both roles for the interactive command/event example.
- `inventory/contracts`: the shared request/reply model.
- `inventory/server`: the runtime-owned durable request consumer.
- `inventory/client`: a client that sends one request, receives its correlated
  reply, and exits.

## Generated roles and runtime

Applications reference `NSmithy.Messaging.Redis` alongside the Bote build
extension. Both examples enable generated DI registration. `IChatRoomClient`
sends commands, `IChatRoomEventPublisher` emits events, and `IPostMessageHandler`
and `IReadMessagesHandler` handle their respective operations. The inventory
owner implements `IGetStockHandler`; `InventoryClient.GetStockAsync` returns its
typed reply. Business interfaces contain no Redis SDK types.

The runtime creates one scope per message. Consumer-group processing uses
`XREADGROUP`, periodically recovers idle pending entries with `XAUTOCLAIM`, and
acknowledges only after processing and any reply publication succeed. Redis 6.2+
is required for recovery. Handlers must tolerate duplicates. `MinIdleTime` should
exceed the time needed to process a fetched set of entries so healthy consumers
do not reclaim each other's work.

Each chat terminal uses independent `XREAD` event handling, starting at the
current end of the stream. Its cursor is in memory for this demo. Configure a
`RedisStreamCheckpointStore` and stable `CheckpointName` to resume after restart;
use a distinct checkpoint per logical reader and only one active reader for each.
The owner-side command consumers share a group, so replicas share the work.

Request/reply subscribes before sending the request and unsubscribes on success,
failure, or timeout. Set `RedisMessagingOptions.RequestTimeout` at the composition
root (the inventory client uses five seconds). Replies use Pub/Sub, so a requester
that disconnects can miss a reply even though the request was processed.

## Prerequisites

- .NET 10 SDK
- `just`, or the repository toolchain through `devenv shell`
- Docker

## Build

Run all commands in this README from `examples/redisjson`. First build the local
packages and examples:

```bash
just build
just pack
just refresh-examples
```

## Run

Start Redis:

```bash
docker compose up -d
```

### Chat

```bash
dotnet run --project chat
```

The process asks for your display name and joins the `lobby` room. Press Enter
at the name prompt to use your local user name. Type messages at the chat prompt
and press Ctrl+C to stop. Optional arguments select the Redis endpoint, room,
and display name without prompting:

```bash
dotnet run --project chat -- localhost:6379 engineering alice
```

### Inventory request/reply

Run the server in one terminal:

```bash
dotnet run --project inventory/server
```

Then perform a lookup from another terminal:

```bash
dotnet run --project inventory/client -- localhost:6379 coffee-beans
```

The host runs its durable request consumer until Ctrl+C.

## Stop

Stop the applications with Ctrl+C, then remove Redis:

```bash
docker compose down
```

## Runtime integration tests

The test suite includes generated Streams request/reply, failed-delivery recovery,
checkpoint resume, and Pub/Sub delivery and cleanup tests. From the repository
root, with a disposable Redis instance running:

```bash
just build
NSMITHY_TEST_REDIS=127.0.0.1:6379 dotnet test tests/Messaging -c Release --no-build
```

These broker tests are skipped when `NSMITHY_TEST_REDIS` is unset. CI starts Redis
and enables them. Pure runtime tests in `tests/NSmithy.Tests/Messaging` cover
failure, cancellation, claim scan pagination, and Pub/Sub overflow without a broker.
