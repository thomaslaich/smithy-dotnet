title: Distributing contracts
description: Share your Smithy model across projects and ecosystems via a NuGet contracts package or a Maven-compatible JAR.
---

Distributing your Smithy model lets other projects consume the contract without
copying model files. NSmithy supports two packaging paths:

- **Maven JAR**: any Smithy-based toolchain (Java, TypeScript, Python, .NET,
  and others) can consume it from a Maven registry. This is the more portable
  option.
- **NuGet package**: contains model files and their Smithy build configuration.
  Consumers currently need explicit MSBuild items to import them.

## Within a solution

Reference a contracts project with `SmithyPublish=true`:

```xml title="MyService.Client/MyService.Client.csproj"
<ItemGroup>
  <ProjectReference Include="../MyService.Contracts/MyService.Contracts.csproj" />
</ItemGroup>
```

Set `SmithyService` in the consumer to select its service. Without an explicit
`smithy-build.json`, NSmithy assembles the referenced sources automatically.

A project generates the shapes in its own model files, so the contracts project
generates the model's types, and it needs the runtime:

```xml title="MyService.Contracts/MyService.Contracts.csproj"
<ItemGroup>
  <PackageReference Include="NSmithy.MSBuild" Version="NSMITHY_VERSION" PrivateAssets="all" />
  <PackageReference Include="NSmithy.Core" Version="NSMITHY_VERSION" />
</ItemGroup>
```

Its consumers reference those types instead of generating their own: a client
and a server of the contract generate only their client or server and share one
set of types. A contracts project that should only validate and package its
model, for example one whose consumers are F# projects, sets
`SmithyGenerateShapes` to `false`; its consumers then generate its shapes.

### Splitting a service across projects

The same rule lets the modules of one server each own their operations. A
module's model defines its operations without a service, and the module
generates their types, schemas, and handler interfaces. It needs only
`NSmithy.Core`:

```smithy title="Shop.Orders/model/orders.smithy"
$version: "2"
namespace acme.shop

@http(method: "POST", uri: "/orders", code: 201)
operation PlaceOrder {
    input := { @required total: Money }
    output := { @required orderId: String }
}
```

```xml title="Shop.Orders/Shop.Orders.csproj"
<PropertyGroup>
  <SmithyPublish>true</SmithyPublish>
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="NSmithy.MSBuild" Version="NSMITHY_VERSION" PrivateAssets="all" />
  <PackageReference Include="NSmithy.Core" Version="NSMITHY_VERSION" />
  <ProjectReference Include="../Shop.Common/Shop.Common.csproj" />
</ItemGroup>
```

The module implements `IPlaceOrderHandler`. One project defines the service,
references the modules, and sets `SmithyService`; it generates only the
service and gets the models of the modules' own references, such as
`Shop.Common` with `Money`, through them:

```smithy title="Shop.Api/model/service.smithy"
@restJson1
service Shop {
    operations: [PlaceOrder]
}
```

A module sets `SmithyPublish` so that its model reaches the projects that
reference it. Every project in the solution must use the same NSmithy version.
See the [shape ownership design](https://github.com/thomaslaich/smithy-dotnet/blob/main/designs/shape-ownership.md).

## Maven JAR distribution

:::tip[Recommended]
Maven JAR distribution is generally preferred. It works with Smithy tooling
outside .NET, so Java, TypeScript, Python, and other consumers can use the same
model package.
:::

<Steps>

1. **Configure.** Add `SmithyMavenGroupId` and `SmithyMavenArtifactId` to the
   contracts project:

   ```xml title="MyService.Contracts/MyService.Contracts.csproj" ins={3-4}
   <PropertyGroup>
     <SmithyPublish>true</SmithyPublish>
     <SmithyMavenGroupId>io.github.acme</SmithyMavenGroupId>
     <SmithyMavenArtifactId>my-service-contracts</SmithyMavenArtifactId>
   </PropertyGroup>
   ```

   `Version` (or `VersionPrefix`/`VersionSuffix`) is reused as the Maven version.

   In the project's `smithy-build.json`, declare the contract's dependencies in
   `plugins.contracts-jar.dependencies`. Include the Maven artifacts providing
   external shapes and traits, but omit code generators and other build tools:

   ```json
   "plugins": {
     "contracts-jar": {
       "dependencies": ["software.amazon.smithy:smithy-aws-traits:1.74.1"]
     }
   }
   ```

   This setting is required. Use `"dependencies": []` when the contract has no
   external dependencies. Keep the corresponding artifacts in `maven.dependencies`
   too, so Smithy can load them during the build.

2. **Pack.**

   ```shell
   dotnet pack MyService.Contracts --configuration Release
   ```

   The build runs NSmithy's `contracts-jar` Smithy plugin, and pack copies its
   JAR, POM, and checksum files next to the NuGet package. The JAR contains the
   model in Smithy's discovery layout. The POM declares the explicitly configured
   dependencies, so consumers get them along with the contract.

3. **Install locally** (optional). To make the JAR available to local Smithy CLI
   builds during development:

   ```shell
   mvn install:install-file \
     -Dfile=MyService.Contracts/bin/Release/my-service-contracts-1.0.0.jar \
     -DpomFile=MyService.Contracts/bin/Release/my-service-contracts-1.0.0.pom
   ```

4. **Publish to a registry.** The files are plain Maven artifacts. Upload them
   with any Maven deploy tool, for example to GitHub Packages, Artifactory, or
   Nexus:

   ```shell
   mvn deploy:deploy-file \
     -Dfile=MyService.Contracts/bin/Release/my-service-contracts-1.0.0.jar \
     -DpomFile=MyService.Contracts/bin/Release/my-service-contracts-1.0.0.pom \
     -DrepositoryId=github \
     -Durl=https://maven.pkg.github.com/ORG/REPO
   ```

   `repositoryId` names the `<server>` in your Maven `settings.xml` that holds
   the registry credentials.

5. **Consume.** The client template defaults to Maven distribution:

   ```shell
   dotnet new nsmithy-client -n MyService.Client
   ```

   Replace the placeholder contracts coordinate in its `smithy-build.json` with
   `io.github.acme:my-service-contracts:1.0.0`. Configure `maven.repositories` in
   that file for a private registry. Other Smithy toolchains consume the same
   coordinate through their Maven dependency configuration.

</Steps>

:::note
Maven JAR distribution does not require a dedicated contracts project. You can
add `SmithyMavenGroupId`, `SmithyMavenArtifactId`, and `SmithyPublish=true`
directly to a server project that owns model files, and `dotnet pack` will
produce the JAR. A separate contracts project is still recommended because it
keeps the model decoupled from any one implementation and easier to share across
server and client projects.
:::

## Outside .NET

`contracts-jar` is an ordinary Smithy build plugin, so a contract owned by a
Python, Java, or TypeScript project is packaged the same way with the Smithy
CLI:

```json title="smithy-build.json"
{
  "version": "1.0",
  "sources": ["model"],
  "maven": {
    "dependencies": [
      "software.amazon.smithy:smithy-aws-traits:1.74.1",
      "io.github.thomaslaich.nsmithy:smithy-contracts-jar:NSMITHY_VERSION"
    ]
  },
  "plugins": {
    "contracts-jar": {
      "groupId": "io.github.acme",
      "artifactId": "my-service-contracts",
      "version": "${CONTRACTS_VERSION}",
      "dependencies": ["software.amazon.smithy:smithy-aws-traits:1.74.1"]
    }
  }
}
```

```shell
CONTRACTS_VERSION=1.0.0 smithy build
```

The JAR, POM, and checksums are written to
`build/smithy/source/contracts-jar/`. Publish them as in step 4. Configure the
plugin in a projection instead to package a filtered model, such as one without
shapes tagged `internal`.

| Setting | Description |
| --- | --- |
| `groupId`, `artifactId`, `version` | The contract's Maven coordinates. Required. |
| `dependencies` | Required list of `groupId:artifactId:version` coordinates to declare in the POM. Use `[]` when no external dependencies are needed. |

## NuGet distribution

<Steps>

1. **Pack.**

   ```shell
   dotnet pack MyService.Contracts --configuration Release
   ```

   With `SmithyPublish=true`, the package contains:

   - the assembly with the types the contracts project generated;
   - the model sources under `build/smithy/` and `build/smithy-build.json`;
   - the shape manifest, `build/smithy/nsmithy-shapes.json`, which lists
     those types;
   - `buildTransitive/<PackageId>.props`, which declares the model and the
     manifest to the projects that reference the package.

   Publish the `.nupkg` to your NuGet feed.

2. **Consume.** Reference the package:

   ```xml title="MyService.Client/MyService.Client.csproj"
   <PropertyGroup>
     <SmithyService>example.hello#HelloService</SmithyService>
     <SmithyGenerateServer>false</SmithyGenerateServer>
   </PropertyGroup>

   <ItemGroup>
     <PackageReference Include="NSmithy.MSBuild" Version="NSMITHY_VERSION" PrivateAssets="all" />
     <PackageReference Include="NSmithy.SmithyCli" Version="1.74.1" />
     <PackageReference Include="MyService.Contracts" Version="1.0.0" />
   </ItemGroup>
   ```

   The project assembles its model with the package's, uses the package's
   types, and generates only its client or server. Projects that reference the
   package without generating code, such as an application that references the
   client library, are unaffected.

</Steps>

Every project that consumes a package's types must use the NSmithy version
the package was built with: generated code from different versions may not fit
together, and the build fails with a message naming both versions. A package
whose consumers should generate its types themselves, for example in their own
namespace or with another NSmithy version, is packed from a project with
`SmithyGenerateShapes` set to `false`. It contains the model only, and its
consumers generate its shapes.

Keep the runtime packages required by the generated client or server. NSmithy
merges the contract's build file into the effective `smithy-build.json` under
`obj/`, invokes `smithy build`, and adds the generated `.g.cs` files to
compilation.
