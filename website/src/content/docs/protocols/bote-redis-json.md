`NSmithy.Bote` generates C# over
[StackExchange.Redis](https://stackexchange.github.io/StackExchange.Redis/) for
the `bote#redisStreamsJson` and `bote#redisPubSubJson` protocols. Add the build
extension and transport library to the generating application:

```xml
<PackageReference Include="NSmithy.Bote" Version="NSMITHY_VERSION" />
<PackageReference Include="StackExchange.Redis" Version="2.8.31" />
```

The NuGet package carries the Bote code generators and their Maven dependency
closure. It depends on `NSmithy.MSBuild`, so consumers do not install Maven or a
JRE.

## Redis Streams

Use `@redisStreamAdd` for commands and `@redisStreamRead` for durable event
streams. A chat illustrates this naturally: the owner accepts commands on one
stream and publishes events on another.

```smithy
@redisStreamsJson
service ChatRoom {
    version: "1.0"
    operations: [PostMessage, ReadMessages]
}

@redisStreamAdd(stream: "chat:commands", maxLen: 10000)
operation PostMessage {
    input: PostMessageCommand
}

@redisStreamRead(stream: "chat:events", maxLen: 10000)
operation ReadMessages {
    output := { messages: ChatEvents }
}

@command structure PostMessageCommand { body: String }
@event structure MessagePosted { body: String }
@streaming union ChatEvents { messagePosted: MessagePosted }
```

The generated `{Service}RedisStreams` type appends commands, publishes event
union members, and exposes stream readers as `IAsyncEnumerable<T>`. The owner
implements `I{Service}RedisStreamsHandler` and runs
`{Service}RedisStreamsConsumer` with a consumer-group and consumer name.

An add operation without an output is fire-and-forget. For a naturally unary
interaction such as an inventory lookup, an output annotated `@reply` makes the
operation request/reply:

```smithy
@redisStreamAdd(stream: "inventory:queries", maxLen: 10000)
operation GetStock {
    input: GetStockRequest
    output: GetStockReply
}

@command structure GetStockRequest { productId: String }
@reply structure GetStockReply { productId: String, available: Integer }
```

The requester subscribes to a temporary Pub/Sub channel
before `XADD`. The stream entry contains `data`, `reply_to`, and
`correlation_id`. One owner replica handles the durable request through the
shared consumer group, publishes a JSON reply envelope to `reply_to`, echoes
the correlation ID, and acknowledges only after the reply succeeds. Requests
may be redelivered after failure; Pub/Sub replies are at-most-once. Generated
request methods default to a 30-second timeout and accept an override.

The runnable [Redis JSON example](https://github.com/thomaslaich/smithy-dotnet/tree/main/examples/redisjson)
keeps these lessons separate: `chat` demonstrates command/event streaming and
`inventory` demonstrates unary request/reply.

## Redis Pub/Sub

Use `@redisPublish` for fire-and-forget commands and `@redisSubscribe` for
event unions. The generated `{Service}RedisPubSub` type publishes typed JSON
messages and exposes subscriptions as `IAsyncEnumerable<T>`. The owner
implements `I{Service}RedisPubSubHandler` and runs
`{Service}RedisPubSubConsumer`. Pub/Sub has no replay or request/reply; use
Redis Streams when either is required.

Command and event traffic must use distinct Redis stream keys or Pub/Sub
channels. Their JSON encodings distinguish event variants, but do not carry a
command-versus-event direction discriminator.

## AsyncAPI

Set `<SmithyGenerateAsyncApi>true</SmithyGenerateAsyncApi>` to generate
AsyncAPI 3.1 and copy it to `wwwroot/asyncapi.json`. Redis Streams replies use a
dynamic `reply_to` channel and declare correlation metadata in the document.
